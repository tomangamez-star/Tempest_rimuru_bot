The v3 deployment entered a Render 502/restart loop because repeated Postgres connection timeouts triggered process termination.

V4 changes:
1. Removed the persistence-failure process termination path. Transient Postgres failures now fence durable writes and keep /health alive.
2. Telegram state-changing commands/callbacks are blocked while persistence is degraded, so SQLite does not continue accumulating unsafe economic changes.
3. Background recovery reconnects to Postgres, validates a real query, rehydrates safely, revalidates/reacquires the primary lock if necessary, and only then re-enables the write pipeline.
4. Added Postgres pool error logging.
5. Prevented full-mirror overlap by awaiting queued table mirrors before another full reconciliation pass can start.
6. Reduced the default full reconciliation interval from 1.5 seconds to 30 seconds. Per-mutation write-through paths remain active; the periodic pass is only a safety reconciliation now.
7. A single successful late write no longer clears a degraded state. Recovery must complete through the reconnect path.

- reintroduce a 1.5-second full mirror loop
- disable the dedicated-session advisory lock
- auto-restore an old backup during recovery
- declare success from local tests alone
